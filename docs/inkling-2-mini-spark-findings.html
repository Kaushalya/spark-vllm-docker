Benchmark report · 26–28 November 2026 · One DGX Spark

Inkling 2 Mini on DGX Spark

DFlash2 raised single-request decode throughput by 37–41% over DSpark, and Humming’s NVFP4 expert kernels added 20% prefill and 3.4% coding decode. Follow-up kernel, profiling, and quantization sweeps on 28 November established a three-tier Pareto frontier: +5.9% coding decode (59.04 tok/s) with 100% target-lossless DFlash2 draft quantization, +31.6% coding decode (73.40 tok/s, 60.11 tok/s at 41K) with Humming MXFP8 dense and coda kernels, and +49.2% high-reasoning decode (75.97 tok/s, 140.3 / 207.9 tok/s at 4/8 requests, 43.2 ms/step) with full Humming NVFP4 target dense, head, and coda quantization.

28 November optimization sweep

Inspecting the pinned vLLM runtime and microbenchmarking individual GB10 kernels exposed three major remaining bottlenecks beyond Humming’s NVFP4 MoE backend:

  1. Unquantized DFlash2 draft weights. The draft model’s 5-layer backbone (~762 MB) and shared BF16 lm_head (~926 MB) ran through cuBLAS BF16 on every speculative step. Because verification always uses the untouched target model, quantizing the draft model and a draft-only copy of lm_head via Humming is 100% lossless to target outputs. On GB10, M=7 draft lm_head latency fell from 4.06 ms (cuBLAS BF16) to 2.11 ms (Humming MXFP8) and 1.17 ms (Humming NVFP4 W4A16, 3.5× faster).
  2. Four MXFP8 coda MoE layers still on Triton. In inkling2/nvidia/moe.py, --moe-backend humming only applied to the 20 NVFP4 layers (44 visits). Layers 20–23 (MXFP8) still ran Triton’s dequantizing kernel. Switching those four layers to Humming MXFP8 W8A16 cut single-layer latency from 1.84 → 1.71 ms at M=8 and 14.62 → 7.53 ms at M=2048 (1.94× faster prefill), while caching moe_align_block_size between w13 and w2 eliminated 44 redundant alignment launches per step.
  3. Target BF16 dense projections dominate decode bandwidth. Across 48 loop visits, dense BF16 attention weights (qkvr + wo_ud = 2.732 GB) plus the target lm_head (0.926 GB) account for roughly two-thirds of single-request target memory reads. Online block-32 Humming MXFP8 W8A16 quantization halves that traffic with minimal numerical drift.

Three recommended profiles. Use inkling-2-mini-dflash2-lossless when strict target fidelity is required (4/4 bitwise-identical greedy hashes; +5.9% coding, +6.5% sampled, +9.2% at 41K). Use inkling-2-mini-dflash2-mxfp8 for peak greedy coding (73.40 tok/s, +31.6%, 36.9% acceptance) and 41K decode (60.11 tok/s) with 8-bit target dense/head/coda fidelity. Use inkling-2-mini-dflash2-nvfp4 for lowest step latency (43.2 ms/step, −26.8% vs. baseline), smallest memory footprint (18.2 GiB, 1.501M KV tokens), and peak sampled reasoning (75.97 tok/s, +49.2%) and concurrency (140.3 / 207.9 tok/s at 4/8 requests).

Trade-offs found in the sweep

  • FP8 KV cache (--kv-cache-dtype fp8). Increased KV cache capacity by +57% (1.45M → 2.28M tokens, 8.71× at 262K) and trimmed 1-request step time by 2–4%, but slowed 32K prefill by 6.5% and 4/8-request throughput by 5–7% due to FP8→BF16 dequantization in Triton’s _load_fp8_kv. Best reserved for high-concurrency or 131K–262K workloads.
  • DFlash2 draft backbone must stay MXFP8. Cold-DRAM CUDA-graph checks showed NVFP4 dense projections run 1.76× faster than MXFP8 when use_stream_k=False (40.8 µs vs. 71.9 µs for 6656×2304), but quantizing the 5-layer DFlash2 draft backbone to NVFP4 (exp8–exp11) lowered acceptance by 3–6 percentage points, hurting net throughput. Keeping the draft backbone in MXFP8 (use_stream_k=False) with an NVFP4 draft head gave the best speed/acceptance balance.
  • NVFP4 MoE W4A16 ruled out. Even with GB10-tuned tiles matching W4A4 bandwidth (~240 GB/s), deterministic W4A16 (exp12) trailed W4A4 on concurrency and prefill and degenerated into repetition on the 94K needle check.
  • Quality verification on mxfp8 and nvfp4. Both exp6 (MXFP8) and exp14 (NVFP4) passed math + reasoning (410), Inkling tool calling (get_weather), and 3-needle retrieval at 30K and 94K tokens (3/3); exp14 also passed the executable Python unittest check. See full 17-config benchmark report for all per-task numbers.

What the other trials showed

  • 4,096-token batch budget. At 25,554 tokens, warmed prefill dropped 5.6%. During concurrent decoding, long-prompt time to first token rose 11% and p95 gaps between stream updates grew from about 765 ms to 1,522 ms. Eight-request throughput rose 5.3% against the median of the controls and 2.8% against the faster control.
  • Adaptive verification. The pinned image rejected variable per-request query lengths during graph initialization. Its Inkling short-convolution backend requires a fixed decode shape.
  • Decode profile. Expert GEMMs accounted for about 53% of summed GPU kernel time across 12 profiled decode iterations. The draft output-head projection accounted for 6.6%, or about 4 ms per iteration. That led to the Humming trial.

Why Inkling needs an adapter

  1. Inkling’s 24 physical layers execute as 48 visits. The draft expects three specific loop visits and the final normalized state. The pinned vLLM image’s generic DFlash route increments the draft’s layer indices. The adapter uses the checkpoint’s [5, 23, 41, 48] convention, where 48 denotes the appended final state.
  2. Sharing the raw embedding table yielded only 1.003 emitted tokens per verification and 15.48 tok/s at one request. Sharing Inkling’s input embedding normalization with the draft restored useful acceptance.
  3. The adapter bounds proposals to Inkling’s usable vocabulary and applies the logit soft cap after the selector’s transition correction. The launcher selects the dflash method and loads the DFlash2DraftModel architecture from Inco AI’s checkpoint.

Inco AI reported around 27–40% higher single-request throughput than DSpark on an H200 with patched SGLang. The values in this report come from the local vLLM runs. Inco AI evaluation

Method and hardware

Shared settings

Host and runtime
One NVIDIA GB10 DGX Spark. NVIDIA driver 580.178.04. vLLM 0.1.dev25855+g7cb5dae22, PyTorch 2.14.0 with CUDA 13.0.
Model and limits
Official Inkling 2 Mini with native mixed NVFP4/MXFP8 expert weights, tensor parallelism 1, 262,144 context tokens, and a 0.8 GPU memory utilization target. The host watchdog used an 11 GiB shared-memory floor.
Generation workload
Six fixed coding, prose, and reasoning prompts. Requested up to 512 output tokens per request, with temperature 0.6, seed 42, and high reasoning effort.

Reading the timing

Single-request decode uses the median of six completion-token rates after the first streamed content. Four-request throughput divides the total output tokens by the time from first request start to last finish.

Prefill uses actual prompt tokens divided by time to the first token. The detailed tables distinguish first-use measurements from three-repeat warmed-kernel medians using fresh prompts. First-use Triton compilation depressed some short-prompt measurements.

The initial 321-second boot served health checks, but the client sent an internal checkpoint path and received HTTP 404. The client subsequently read the public model ID from /v1/models.

The bandwidth model budgets 2.732 GB of dense tensors, 0.926 GB for the output head, and 1.839 GB of routed expert weights for a short single-token target step. The short target-pass bandwidth floor is about 26.6 ms before scheduling and tokenization. Speculative verification can emit several tokens per target pass.

Across the 48 visits, eight use full attention and forty use a 1,024-token sliding window. The logical BF16 target KV minimum is 8.16 GiB per 262,144-token sequence. Engine allocation also includes draft state, convolution state, block grouping, and workspace. The BF16-equivalent prefill estimates use half the measured GEMM rate and omit scheduler and kernel overhead.
